# 设备首个/第二个账号的固定样本对照

入口为 `GSA设备顺序对照.command` 或 `.venv/bin/python gsa_device_order_study.py`。读取本机自有账号文件，代理 API 隐藏输入，详细调试默认开启。支持最多 20 个账号，实际认证并发不超过 2。

首轮两两分组：

```text
新设备 1 + 新代理 → 账号 1 → 账号 2
新设备 2 + 新代理 → 账号 3 → 账号 4
……
新设备 10 + 新代理 → 账号 19 → 账号 20
```

同一对账号保持设备身份和代理端点不变。每个账号刷新自己的动态认证参数，并使用独立的 GSA HTTP 会话。通过公网 IP 查询记录观察到的代理出口；代理租约剩余时间不足时不强行继续，结果标为未测试或超时，不能视为设备拒绝。

完成首轮后，将 init/-20970 或临时网络/超时问题的账号写入 `failed-queue.json`。每个入队账号最多再分配一次新设备、新代理，并作为该设备的首个账号复试。密码错误、账号锁定、未激活、密码证明通过和需要二次验证等明确结果不自动复试；complete 阶段的 -20970 不套用 init 的重试策略。

固定预算：最多 40 次账号认证调用，最多 30 台新设备，每个账号在本次实验内最多两次。没有无限换设备或 IP 循环。任何阶段的 HTTP 429 会停止实验并回收子进程。账号锁定只停止该账号的后续认证。

实验在生产设备池当前冷却到期后启动。使用独立的 `config/device-order-studies/` 目录，保留原设备及健康记录。为完成固定样本对照，本实验目录不启用生产入口的“三台设备拒绝即暂停”规则，改由上述固定样本预算约束；生产入口原规则不变。

公共配置、Anisette 参数服务及其 WebSocket 直连；Apple 注册和 GSA 认证始终使用该实验单元领取的代理。代理按需逐条获取，60 秒有效期，整个设备实验单元在有效期到期前由父进程回收。父进程调度并监督最多两个设备实验单元，另一个供给线程负责限时代理提取。

输出目录为 `logs/order-study-时间-进程号/`：

- `events.jsonl`：设备创建、账号顺序、代理指纹、IP 检测、阶段和错误码。
- `results.jsonl`：每个账号每轮的结果、设备号、在该设备上的位置、耗时和密码证明状态。
- `failed-queue.json`：需要新设备复试的账号序号。
- `summary.json`：首个账号、第二个账号、新设备首个账号三组统计，以及逐账号标记。
- `debug.jsonl`、`debug-summary.json`：无正文的网络、注册、SRP 和进程诊断。

“初始化被接受”和“密码认证通过”分开统计：进入 complete 可以说明 init 已被接受，只有 M2 校验通过才能确认密码证明。代理出口查询是其他 HTTPS 服务观察到的地址，不是 Apple 服务端提供的出口证明。同一代理端点下若观察到出口变化，不能把该对数据视为严格保持出口不变的对照。

本实验是有限样本的观察，不能从几次结果推断 Apple 存在固定的“第几个账号封禁”规则。既往第一轮的设备 1、2、3 在首个账号上均出现过 init/-20970，未观察到“首个必然成功”。
