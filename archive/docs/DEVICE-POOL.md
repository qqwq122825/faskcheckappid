# 5 台设备的持久化测试工具

双击 `GSA设备测试.command`。设备编号 1–5 固定对应独立的设备注册状态。输入 `p` 准备五台设备，输入编号选择该设备并认证，输入 `r` 只测试设备参数刷新，输入 `q` 退出。

## 终端使用

```sh
cd /Users/xxx/Documents/并发

# 首次准备 5 台设备；已注册编号直接复用
.venv/bin/python gsa_devices.py prepare --count 5

# 查看本地状态，不联网
.venv/bin/python gsa_devices.py list

# 只测设备 2 的参数刷新，不提交账号
.venv/bin/python gsa_devices.py refresh --device 2

# 选择设备 2；账号密码只在本机交互输入
.venv/bin/python gsa_devices.py login --device 2

# 只尝试一轮，便于和原单账号脚本比较耗时
.venv/bin/python gsa_devices.py --attempts 1 login --device 2

# 重新同步该服务的客户端配置
.venv/bin/python gsa_devices.py prepare --refresh-info
```

全局参数放在子命令前：`--anisette-url`、`--pool-dir`、`--timeout`、`--prepare-timeout`、`--attempts`。

## 架构

```text
每个 Anisette 服务独立分区
  ├─ client-info.json       客户端配置缓存，所有设备配套复用
  ├─ health.json            设备拒绝次数、冷却时间、服务异常窗口
  ├─ measurements.jsonl     仅保存编号、耗时、结果类别、阶段和错误码
  └─ devices/
       ├─ 01/              设备 1 的 identifier + adi_pb
       ├─ 02/              设备 2 的 identifier + adi_pb
       ├─ 03/
       ├─ 04/
       └─ 05/
```

默认根目录为 `config/device-pool/`，服务分区按规范化服务地址的哈希命名。注册状态使用提取的原始 `StateStore` 保存，JSON 文件权限 600，设备目录权限 700。状态文件不保存账号密码，测量文件也不保存邮箱、密码、OTP、注册数据或响应正文。测试工具面向当前 macOS / POSIX 环境，设备使用权通过文件锁在多个进程间互斥。

注册顺序执行，新增设备之间默认间隔 3 秒，任一失败会停止本次准备，已成功状态保留。重新运行时复用已有编号。认证入口要求完整的注册状态；状态缺失或损坏时不会静默创建另一个设备。

## init/-20970 的处理

该码按“初始化被拒”记录，不能只凭它认定设备被封。下列阈值为测试工具的本地策略，没有声称是 Apple 的封禁阈值。

1. 只对 `init` 阶段的 `-20970` 以及临时网络/TLS/服务错误进行有限重试。默认最多两轮（第一次加一次重试），可设为 1–3 轮。
2. 每轮刷新 Anisette 参数，保持同一设备身份，关闭上一轮 HTTP 会话，再建立新的 GSA 会话。init 和 complete 使用同一份参数及同一个会话。
3. 重试间隔为指数退避加少量随机抖动，退避耗时单独显示。设备使用权覆盖整次操作，重试期间其他进程无法同时领取这台设备。
4. 同一设备累计 5 次尚未恢复的 `init/-20970` 后，冷却 600 秒。中间网络错误不证明设备已恢复，明确进入 complete 阶段才清除此初始化拒绝计数。
5. 冷却到期后，该设备只进行一轮恢复尝试；再次被初始化拒绝就继续冷却，进入 complete 后恢复。
6. 同一服务 60 秒内有 3 台不同设备出现 `init/-20970`，打开服务熔断 600 秒，后续任务停止领取该服务的设备。已经在途的网络请求不会被这个检查强行中断。
7. 服务熔断到期时，通过服务级文件锁只允许一个操作验证恢复。若再次出现初始化拒绝，重新打开服务熔断；明确进入 complete 后恢复正常分发。

HTTP 429、密码错误、账号锁定、需要二次验证、complete 阶段的 -20970 都不自动重试。账号锁定停止当前账号。本工具不会自动切换设备或更换出口继续尝试，也不会自动删除状态、重新注册设备。cooldown 期间不额外发送探测账号请求，只在用户下一次正常操作时检查是否允许恢复。

跨设备重复拒绝也可能与请求涉及的账号或公共配置有关，不能据此证明服务故障或设备被封；服务熔断的作用是暂停继续发送，保留现场。

## 如何比较速度

原单账号入口在输入前联网准备一次，输入后再刷新一次。此工具提前完成注册并缓存客户端配置，选设备时读取本地状态，输入后仅获取一次新鲜参数，再进行 GSA 认证。

观察三项：本地加载、参数刷新、GSA 认证；发生重试时再比较轮数、退避及总耗时。新设备注册时间不会算作后续单账号认证时间。不同设备不必然更快，也不保证降低服务端拒绝率；仍需在同样网络、尝试次数和账号条件下比较实际结果。

本页的单设备测试入口仍使用直连。新增的代理池、设备供给线程、两个认证进程及可选详细调试入口，见 `BATCH.md`，双击 `GSA批量测试.command`。它使用独立的设备目录，不改变本页五台直连设备的状态。账号密码由调用方提供，调用结束后不持久化。

原项目仅实现密码证明及二次验证状态判断，尚不提交验证码或导出业务登录令牌。

## 验证

```sh
.venv/bin/python -m unittest discover -s tests -v
```

已通过 21 项离线测试，使用独立的合成 SRP 服务和设备服务替身，禁止网络连接；覆盖设备状态隔离、重启复用、客户端配置缓存、所选编号、有限重试、5 次冷却、服务多设备熔断、恢复互斥、耗时写盘失败不覆盖认证结果，以及账号错误和 429 不重试。

已实际注册 5 套不同身份，首次总准备 53.11 秒（含新增设备间隔）；重启复用的本地准备为 2.55 毫秒。5 台设备各测试一次参数刷新，均成功，耗时约 1.05–3.07 秒。交互菜单已在终端验证可列出并选择编号。无凭据摘要见 `gsa_protocol/device_pool_validation.json`。

尚未用真实账号比较该工具的认证速度或 -20970 比例，不能由设备注册成功、参数刷新或离线测试推断其改善幅度。
